# Architecture

## Milestone 7 assistance providers

Electron main owns a single serialized `Assistance` manager behind the validated preload bridge. Provider adapters share the same strict commands and post-response supplied-ID validation. `none` dispatches nothing; Ollama remains loopback-only; OpenAI uses the official SDK Responses API with strict JSON schema, `store:false`, no tools, bounded time/output, `maxRetries:0`, and an `AbortSignal`. Provider changes and credential mutation are blocked while a request is active; there is no automatic provider fallback.

Only bounded workflow issue/input/header/candidate metadata selected by an explicit user action is sent. The renderer shows a provider-specific disclosure and exact example payload. Output remains untrusted guidance requiring explicit acceptance; it cannot clear validation, save, inspect, record, or execute. Windows persistent credentials are encrypted by Electron `safeStorage`/DPAPI beneath the configured E: data root. The preload exposes save/remove/status operations but never returns key material; unavailable secure storage has no plaintext fallback.

## Milestone 6B — unsigned assisted NSIS installer

Electron Builder 26.0.12 wraps the existing production payload as a per-user offline NSIS installer. A stable `appId` identifies upgrades. The installer is assisted (`oneClick:false`), permits an explicit E: destination, does not request elevation, create shortcuts, launch after completion, publish, sign, auto-start, collect telemetry or download application/runtime dependencies. Installed resources remain read-only under `resources/app`; `ROUTINE_STUDIO_DATA` and the packaged E: default remain the only writable roots. Uninstall removes the application payload and deliberately leaves external application data intact. There is no automatic data-deletion option. Unsupported downgrades are not guaranteed.

The installer build pins npm, Electron and Electron Builder caches/temp to E:. Normal Windows executable launch and installer mechanisms can write ordinary OS-managed process/prefetch/installer bookkeeping outside E:; the application payload, build inputs, test installation and user data remain on E:. The actual lifecycle test uses a separate synthetic database, creates workflow/revision/raw recording/dataset/mapping/batch/run history, closes and backs up SQLite, upgrades 0.6.0 to 0.6.1, restarts, uninstalls, confirms data retention, reinstalls and reopens the retained data. No suitable local Windows VM/Sandbox was available, so this remains same-machine—not clean-machine—evidence.

## Milestone 6A — unsigned unpacked Windows candidate

`@electron/packager` 20.1.1 produces an unpacked x64 Windows folder with ASAR disabled so production bundles, child/CSV workers, preload, MV3 extension and synthetic CSV resources remain directly auditable. Packaging prunes development dependencies and excludes source directories, docs, scripts, `.git`, `.runtime`, artifacts and caches. Playwright is a production runtime dependency, but its Chromium binary is deliberately external.

`app.getAppPath()` is the read-only resource root (`resources/app` in this candidate). It resolves `out/main/worker.js`, `out/main/csv-worker.js`, `out/recorder-extension` and `fixtures/csv/packaged-customers.csv`. No runtime path depends on the source checkout. Application state resolves from `ROUTINE_STUDIO_DATA`, or `E:\Routine Studio Data` for a packaged default. The path must resolve to E: and be creatable; startup fails clearly otherwise. Electron user/session/log/crash paths, SQLite, profiles, caches, downloads, temp, recorder session copies and exports all live below that data root. Native exports default to `dataRoot/exports`, never application resources.

`ROUTINE_STUDIO_BROWSER_PATH` selects the external E: Playwright browser directory and is exposed with resolved executable/readiness in the narrow status bridge. Missing Chromium is an actionable Not Ready state; browser operations then fail clearly, while the editor/persistence remains usable. Ollama remains optional and unmanaged. No browser/model is downloaded or bundled.

The candidate was copied to an independent E: directory containing spaces and launched by its renamed executable. Actual packaged Electron used the extension, CSV worker, execution worker, external Chromium, demo resources and SQLite across restart. Source directories/dev servers were absent from the package and the built main bundle contained no hard-coded source checkout path. This is same-machine evidence, not clean-machine verification. The executable has no Authenticode signature.

## Milestone 5 — bounded local configuration assistance

Electron main owns `Assistance`, the only Ollama client. Its origin parser permits unauthenticated `http` loopback (`127.0.0.1`, `localhost`, `::1`) only; credentials, paths, queries, remote hosts, TLS endpoints and redirects are rejected. The fixed existing model is `qwen3:8b-q4_K_M`. Requests are serialized with one `AbortController`, a 20-second deadline, 32 KiB request/context, 64 KiB transport response, 4096 context tokens and 700 output-token cap. There is no pull, server lifecycle management, cloud fallback, retry or prompt/response persistence.

Strict shared Zod schemas cover mapping, explanation and target requests/results. Mapping output may reference only supplied stable input/column IDs, once per input. Target output may rank only supplied candidate IDs; unknown/duplicate IDs, extra fields or oversized text reject the whole response. Imported headers/page descriptors are untrusted prompt data. Model text cannot call IPC, mutate validation/readiness, run a browser or authorize execution.

The existing recorder/inspection owner locally extracts at most 100 visible ordinary top-level descriptors from the required currently open page. It never reads input values and excludes hidden/password and recognized payment/authentication elements, full HTML, cookies, unrelated text, frames and shadow DOM. Candidate locators use only the existing enumerated locator schema. Highlighting calls existing read-only inspection. Applying a candidate changes only the renderer draft; saved revisions, raw evidence and run/batch snapshots remain immutable.

Mapping and target UIs retain suggestions ephemerally. Individual acceptance is required, existing bindings use an explicit replacement action, and discarding restores the pre-suggestion mapping draft. Ordinary validation remains authoritative. Offline issue explanations use deterministic local guidance. Reduced-motion styling disables assistance-panel transitions/animation.

## Milestones 4A/4B — data preparation and sequential supervision

`csv-parse` 7.0.3 runs in `out/main/csv-worker.js`, a Node worker thread separate from the renderer/main event loop. Main's native file dialog grants a single explicit import choice on E:. File bytes are bounded to 2 MiB, decoded with fatal UTF-8 handling, parsed without casting/evaluation/implicit trim, and validated by shared `packages/batch-schema`. Limits are 1000 data rows, 50 columns, 160-character nonblank/unique headers, 10000 characters/field and 100000 characters/record; parsing has a 10-second deadline. Structural/encoding/quoting/width errors fail the import without partial silent skips. Source UUIDs, CSV record numbers and physical line ranges persist; multiline fields preserve embedded newlines. No browser is opened for preparation/preview.

Main `DataStore` owns explicit dataset/mapping save/delete operations with optimistic revision checks. Migration v6 adds datasets/mappings/batches; v7 adds separate run investigation notes. Existing workflow/revision/recording/run bytes are not rewritten by these migrations. Mappings keep private dataset and authentic saved-workflow snapshots, stable input-ID bindings to column indices/constants, and explicit per-input trim flags. Changing the source library or workflow never silently updates a saved mapping. Preview shares `actualInputs`/configuration checks with standalone execution; required/optional/simple-email/length/sensitive-name rules and no sample fallback remain consistent. Tables use 20-row pages. The UI marks preparation changes unsaved and protects navigation/window close; deletion confirms and explains retained historical snapshots. All imported cells—including unmapped columns—are plaintext local data, not a secret store.

`Batches` owns one batch-wide reservation and durable `BatchStore` snapshot/state. Preflight validates included/excluded source UUIDs, source values, workflow identity, step limits and per-row plans against the immutable mapping. Batch limits are 100 valid selected rows, 100 steps/row and an 8 MiB snapshot. User-reviewed settings bound step (1–15 seconds, default 8), row wall time (10–300 seconds, default 120), and total wall time (10–3600 seconds, default 1800). Pauses and approvals count toward row/total wall time; origin wait is independently capped at 60 seconds. Invalid/unselected rows are explicitly excluded, never dispatched. Explicit approval and Start persist before work begins.

The orchestrator calls `Runner.prepareSnapshot/start` one row at a time; it does not implement locators, browser actions or assertions. The same worker, fixed matcher, unique-target requirements, assertion semantics and private validated IPC are reused. Each row starts a new Playwright context/page and explicit navigation with the dedicated persistent execution profile. Cookie/login and application state are intentionally shared; no row-isolation or exactly-once claim. Recording, inspection, standalone runs and batch row gaps cannot compete for ownership. Unknown-origin approvals apply to one row only; another row must ask again rather than silently expanding scope.

Main persists the execution worker's PID/run lease in metadata before initialization. A new main process probes that lease: alive/unconfirmed PIDs block takeover and browser modes; a confirmed absent PID clears the stale lease. Exit events clear the current lease. PID reuse can conservatively block progress; no unverified process is automatically killed. Browser profile locks offer an additional launch safeguard. Runner still persists each dispatch before action and each result afterward. Batch rows reference those durable run journals for exact step events/timestamps and keep their own outcome/dispatched/uncertainty state. Startup marks all unfinished batches/runs interrupted and starts nothing.

Default row policy pauses on definite failures. Explicit continue policy only advances to queued rows after definite failure, never retries. Uncertain/interrupted rows always pause; normal Resume is rejected there. Stop prevents later dispatch, marks queued rows not run and is not rollback. Remaining-only work requires a stopped/interrupted/completed parent, confirmed prior worker exit and explicit uncertainty acknowledgment; it creates a NEW immutable review with NEW run IDs and excludes every row with any earlier dispatch. Partial/uncertain rows never receive a convenient retry. This is limited supervised continuation of never-dispatched work, not automatic recovery/reconciliation.

Batch and standalone history retain original snapshots after source edits/deletion. Exception filters separate definite and uncertain/interrupted outcomes; row timelines expose configured evidence, not invented business success. Notes/acknowledgments are separate metadata and never rewrite outcomes. History lists newest 200 summaries; retention/deeper history UI remains deferred, while startup reconciles interruption labels for all stored batches. Investigation does not establish database correctness.

Native save dialogs restrict exports to explicit E: choices. Summaries are point-in-time rows/statuses/settings/notes/approved inputs, not profiles, cookies, full HTML or unmapped source data. JSON retains string values. CSV quotes cells/doubles quotes, includes BOM/CRLF, and prefixes apostrophes before leading formula operators after whitespace/control characters, plus initial tab/CR/LF. This export-only transformation leaves historical inputs unchanged. Exporting does not execute imported content.

The disposable demo adds two clearly labeled names: `DEMO-REJECT` returns a rejection without a customer; `DEMO-DELAY` persists one customer then delays its HTTP response 15 seconds. Runtime has no demo-data read/grader shortcut. Only independent verification code audits customer files to check exact creations/no repeats. Actual UI screenshots and optional short preparation videos are test artifacts on E:, never automatic runtime capture.

Current completed scope: Milestones 0–6B. Optional bounded local configuration assistance remains without execution authority and manual operation remains complete offline. The unsigned installer is locally verified on the same machine only. Unattended real-site use, automatic reconciliation, signing, clean-machine qualification and release publication remain outside the authorized scope. Earlier evidence is explicitly archived.

## Supervised execution (Milestone 3)

`packages/execution-schema` defines strict bounded pre-run, run journal and main/worker schemas. Main loads the requested current saved revision, runs configuration validation, validates actual inputs without sample fallback and prepares a deep parsed immutable snapshot. Resolved ordered fills and reviewed navigation origins are checked against that snapshot. Incomplete drafts remain editable/saveable but cannot execute. A separate explicit Start is required; preparing a review performs no browser action.

Main `Runner` owns one active run and dispatches one step at a time. `RunStore` persists the snapshot, actual inputs, events, in-flight index, pause/stop flags, origin request and terminal state. Migration v5 adds `runs` without rewriting workflows, raw recordings or revisions. Snapshot replacement is rejected; workflow edits/deletion do not rewrite run history. Dispatch commits before sending the step to the child; completion/failure commits afterward. Error details are bounded static messages without Playwright call logs, HTML, passwords or automatic screenshots. Snapshots/values are local plain text, not secret storage.

electron-vite builds `out/main/worker.js`; main forks it with Electron's Node mode and private process IPC. Both directions validate strict messages, UUID run identity, contiguous sequence numbers and expected step state. No renderer JavaScript, arbitrary browser commands or execution command server exists. Production exposes no worker debugging port; test-only ports/pids support real-browser verification. Heartbeat loss (15 seconds), a dispatch watchdog (80 seconds), malformed/session-mismatched messages or child exit interrupt dispatch. Startup marks unfinished journals interrupted; an unfinished dispatch remains uncertain. Nothing automatically resumes or retries. Full reconciliation remains deferred.

The browser manager grants one exclusive lease. Recording/inspection reject during execution; Start rejects active/unsaved recording or busy inspection. Inspection-only contexts close before execution. Worker Chromium uses a separate E: `execution-profile`, `execution-cache`, `execution-downloads` and E: temp paths, without the recorder or everyday profile. Login state is not shared with recording/inspection. Browser closure, extra tabs/popups, dialogs and downloads interrupt execution; service workers and WebSockets are blocked. Shutdown closes Chromium and releases the lease after worker exit.

Fixed internal Chromium CDP Fetch interception pauses each HTTP(S) request, including every redirect hop. Initial scope is exactly the navigation origins shown in review. An unreviewed top-level destination is held before transmission while main persists the request and the user approves/denies. Approval expands only that run's scope; an unanswered request expires after 60 seconds. Unreviewed resource origins are blocked with bounded warnings. Frame navigation is blocked; top-level navigation outside a dispatched step interrupts. This is support for ordinary supervised forms, not a sandbox for hostile pages or arbitrary network behavior.

Inspection and execution share `domTargets`: ordinary CSS, exact normalized labels/role names and enumerated stable attributes, no coordinates or alternative fallback. It excludes tool-owned elements, never enters shadow roots/frames and caps matches at 2000. Fill/click require exactly one target and recheck the same element remains unique before a single action call. Native text-like inputs/textareas and native buttons/HTTP links/checkbox/radio execute. Sensitive/hidden metadata is rejected without reading field values. Heuristics cannot detect every secret: use synthetic/nonsecret inputs. An invoked action followed by failure/timeout is conservatively uncertain; no automatic retry. Playwright may wait for actionability of that same element but never resolves an alternative.

Navigation/actions have an 8-second active budget, excluding bounded approval waits. Explicit checks poll for 6 seconds: zero matches can become one; multiple matches fail. Visibility means nonzero box/display/visibility; opacity/occlusion are not checked. Exact/contains text is case sensitive after whitespace collapse/trim, capped at 10,000 target-text characters. Inspection additionally verifies required page identity and never navigates; execution follows ordered navigation in its original tab under approved scope. Neither a unique match nor a met UI assertion establishes semantic/database correctness.

Pause applies between dispatches; an in-flight action may finish. Stop prevents later dispatch and denies held origins; it is not undo. Terminal outcomes distinguish configured steps completed, assertion failed, action failed, stopped and interrupted/uncertain. No-check workflows warn explicitly. The independent disposable customer-file grader exists only in the execution test, never runtime success logic. The single-row engine has no CSV loop; the Milestone 4 orchestrator below reuses it. No model assistance, automatic reconciliation or installer is included.

## Process boundaries

Electron main owns SQLite, recording/browser lifecycle, read-only inspection, durable run dispatch and privileged operations. A separate TypeScript worker exclusively owns execution Chromium. The sandboxed React/TypeScript renderer accesses a narrow typed contextBridge API for workflows, recording Start/Stop/Cancel/status/save, opening an inspection-only browser, checking a bounded locator and the disposable demo. No arbitrary JavaScript, browser-command, shell or filesystem APIs are exposed. IPC checks the sender, main frame and renderer URL. Zod validates documents in the UI, on save and after loading. Node integration is disabled; context isolation is enabled. Electron renderer navigation, new windows and permission requests are denied. Production uses local assets and a restrictive CSP.

electron-vite builds main, a sandbox-compatible CommonJS preload and the Vite/React renderer. Vite separately bundles the TypeScript MV3 worker/content script. The desktop UI uses local assets without a web server. Two bounded loopback listeners are justified by Milestone 1: an optional disposable demonstration site and an authenticated event-only recorder channel. Both live inside main; there is no Python, general-purpose command server or separately deployed microservice. React Flow visualizes ordered draft steps; list controls reorder them.

## Storage

Default root: E:\projects\routine-studio\.runtime\data. It contains workflows.sqlite, userData, sessionData, cache, logs and crashDumps. Temp files use .runtime/temp. setup.ps1 and run.mjs configure E: caches. Electron's runtime executable is under node_modules/electron/dist on E:.

SQLite uses WAL, synchronous FULL, foreign keys and immediate save transactions. Database v1 creates workflows/revisions; v2 adds a durable example-seeded marker; v3 adds separate raw recording documents; v4 explicitly migrates latest workflow documents to format v2 and backfills target provenance where recorded action order/page/selector can be matched. Migration preserves valid IDs, revision numbers and timestamps, and never rewrites original raw recording or historical revision bytes. Deleted examples do not return. Future database versions are rejected. Saving a recording atomically inserts a new workflow, revision and validated raw recording. Recording-save rejects existing workflow IDs/nonzero revisions. Stale ordinary editor writes fail. Deletion cascades revisions and associated raw recordings.

Workflow document format v2 retains the v1 UUID/title/description/example/revision/timestamp/step/input structure. It adds input requirement/text validation, preferred locator and original target provenance/alternatives, and optional explicit expected-text conditions. Step/input UUIDs stay stable. Fill values reference input UUIDs or literal text. Renaming inputs preserves references; referenced inputs cannot be removed. Unknown legacy steps are retained as bounded unsupported JSON wrappers. Unknown workflow versions and unsafe structural corruption are rejected. Database and document versions are separate.

## Milestone 1 recorder

The implemented recorder launches Playwright's bundled Chromium in a persistent context with the MV3 extension loaded. It reuses compatible E:\AI\Caches\ms-playwright\chromium-1248. The dedicated automation-profile, automation-cache, downloads and session-specific extension copies are under the application data root on E:. Everyday profiles are never read. Downloads are not accepted, and their configured destination stays on E:.

Isolated content scripts operate only after the extension worker confirms an explicit active session and the original tab ID. The worker checks sender tab/frame, validates payloads, serializes them into one global sequence and maintains per-document sequencing. Chrome session storage preserves counters through MV3 worker suspension. Content scripts send pending fills before click/navigation, coalesce changes at blur/change/Stop, and deduplicate a submit click against the resulting submit event. Full-document navigation is captured without queries/fragments. No assertions are invented. Select changes are warned about rather than extending the workflow schema.

Targets retain bounded label, role, stable attribute and fieldset candidates, plus an editable CSS selector. Structural fallback warnings explain fragility. Sensitive/hidden field checks occur before reading .value, then again through shared schemas in the worker and main. Heuristics are intentionally conservative and cannot recognize every unlabeled secret. The recorder never requests cookies, complete HTML, page screenshots or unrelated browser history.

### Session-bound transport

Main opens an ephemeral 127.0.0.1 listener with only POST /event, /warning and /heartbeat. Each session has a random 256-bit bearer capability written only into its isolated extension worker copy on E:. Main pins the exact chrome-extension:// origin discovered from that worker, validates the session UUID, strict schemas, body-size limits, contiguous global/per-document sequence, event count and lifecycle state. No CORS allowance or general browser/filesystem/shell command route exists. Page scripts cannot read the worker's secret. Same-account malicious local processes are outside this isolation boundary; this is not a host-malware defense.

The channel exists only during capture/flush. Stop flushes final text, disables the extension and browser banner, revokes the token and closes the listener before review. Browser remains visible after normal Stop; Save/Cancel closes it. Cancel persists neither events nor a workflow. Heartbeat loss (approximately 10–12 seconds), target closure or browser closure creates a warned partial review and closes the managed context. Cleanup is serialized so another recording can reuse the dedicated profile safely. Lifecycle calls have bounded waits. App close confirms loss of an unsaved recording, then closes Chromium/listeners before SQLite shutdown. Unsaved raw recording recovery after abrupt OS/process kill is not implemented; execution journaling/recovery labeling is described above.

### Review and persistence

Raw recording format v1 remains separate from workflow format v2: session UUID, timestamps, immutable filtered events and warnings. Main normalizes a fresh editable workflow for review. The renderer can edit labels, selectors and values, remove steps and convert literal fills into stable input references. Raw events are not rewritten by review/configuration edits. Both documents are schema-validated before atomic save. Recording review has no overwrite or inferred-success mode; execution is a separate explicitly approved feature.

### Test boundary

Only ROUTINE_STUDIO_TEST=1 enables a Chromium CDP port and privileged main-process test inspection. Neither is exposed through the preload bridge or enabled during normal launches. End-to-end tests click the actual app and interact with real Chromium pages; malformed transport messages are used only for rejection checks. Native dialogs are captured with PrintWindow on their own HWND, avoiding screenshots of unrelated windows.

## Milestone 2 configuration and inspection

WorkflowDraftSchema validates bounded safe representation. It allows empty/invalid URLs or targets, unresolved references and invalid-but-bounded input settings so incomplete work remains saveable. validateWorkflow separately reports blocking configuration issues and review warnings; WorkflowSchema additionally requires blocking issues to be resolved. Duplicate IDs, wrong structural types and oversized documents are rejected. Unsupported legacy steps retain their exact original JSON rather than being dropped. Configuration-ready means these schema/configuration checks passed, never tested execution.

Preferred locators use CSS, exact normalized labels, bounded native/explicit-role name candidates, or enumerated stable attributes. CSS is parsed with css-tree, bounded to 1000 characters, and limited to ordinary selectors/simple structural pseudo-classes; no pseudo-elements, XPath, shadow piercing, arbitrary JavaScript or extended Playwright selector engines are accepted. Original alternatives and recording UUID/event/page/selector/candidates remain separate from preferred edits. Main restores immutable original alternatives/provenance when saving an edited recorded step. Missing/unmatchable legacy provenance is a warning, never fabricated evidence.

Opening an inspection browser launches the dedicated persistent profile without loading a workflow URL. The user must navigate manually. Inspection uses only the manager's original supported Page reference, never arbitrary tab IDs. Required page identity compares origin, pathname and query (fragment ignored). Missing/wrong pages produce an instruction to open the URL, with no navigation. Starting/active/stopping recording states reject inspection at the main-process boundary.

Inspection evaluates a fixed trusted DOM matcher with validated data only. CSS uses document.querySelectorAll; label/role candidates use native form labels, aria-label/labelledby, native/explicit roles and normalized text. This deliberately bounded matcher is not a full accessibility-name implementation. It never enters frames or shadow roots. Counts include hidden elements, exclude inspector-owned nodes, reject over 2000 matches and highlight at most 20. Highlight overlays are fixed, pointer-events:none, temporary (~1.8 seconds) and cause no layout changes. The operation never clicks, fills, submits, scrolls the browser target page or navigates; one match is not semantic proof. The browser uses a blue INSPECTION ONLY banner, distinct from the red recording banner. Inspection results are transient and never create workflow revisions.

Input IDs remain stable through renaming. Multiple fills can share an input; changing back to Literal copies its sample into editable text. Required/optional, simple Email/Text and whole-character 0–10000 validation are configuration rules; invalid bounded settings remain blocking issues. Samples are local plain text and never a secrets store. Explicit assert-visible steps are user-added only. Expected text is exact/contains, case sensitive, with collapsed/trimmed whitespace; no regex. Visibility is a nonzero box, display not none and visibility not hidden/collapse (opacity not evaluated). Checks execute only in explicitly started runs; visible UI state does not establish database correctness.

Saves compare canonical content excluding revision/updatedAt. A no-op save returns the existing document unchanged; actual content changes create one new revision. Optimistic revision conflict checking still applies. Read-only inspection and validation do not save or mutate immutable recording evidence.

## Limits and references

SQLite is synchronous for bounded draft documents. Revisions have no history UI. No signed installer, automatic reconciliation or secrets store exists. Explicit remaining-only reviews do not reconcile uncertain writes. Packaged installation is unverified. Production currently uses file assets; a custom application protocol is future distribution hardening.

Official references checked: https://electron-vite.org/guide/, https://www.electronjs.org/docs/latest/tutorial/security and https://playwright.dev/docs/chrome-extensions. Playwright's extension guide requires a persistent context and its bundled Chromium; Chrome/Edge no longer provide the needed sideload flags.
